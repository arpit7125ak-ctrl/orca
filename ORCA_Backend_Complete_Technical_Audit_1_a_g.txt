SCOPE AND STATUS LEGEND

This document consolidates the backend and integration work developed
across the ORCA project conversations. It records concrete files,
functions, API contracts, configurations, external integrations, tests,
observed failures, and unfinished work.

Status labels: [IMPLEMENTED] = code was created. [TESTED] = behavior was
exercised in the conversations. [PARTIAL] = implemented but not fully
verified or incomplete. [PLANNED] = required by the architecture but not
completed. [KNOWN GAP] = currently differs from the intended final
architecture.

The authoritative ORCA team rules define: - Frontend/ as the Frontend
developer’s ownership area. - AI-Service/ as the AI developer’s
ownership area. - Backend/, GIS-Service/, Ecosystem-Service/, Data/,
Docs/, Scripts/, .github/, root configuration, and
integration/deployment as Arpit’s Backend/Integration ownership. -
Frontend -> Backend API -> internal services/AI. - Backend -> AI-Service
through an agreed contract. - Frontend never calls AI directly. -
Backend = API/orchestration/persistence. - AI-Service = reasoning. -
GIS-Service = spatial processing. - Ecosystem-Service = ecosystem
retrieval. - Multi-zone is mandatory and stable zoneId must be
preserved. - Environmental values, risk, confidence, timestamps,
sources, and AI results must never be fabricated. - Missing data must be
explicitly represented. - Partial failures must preserve successful
data.

SYSTEM ARCHITECTURE & TECH STACK

1.1 PRIMARY ARCHITECTURE

The backend is the central application server, API gateway,
orchestration layer, integration layer, and MongoDB persistence
coordinator.

Required flow:

    HTTP Request
        ->
    Middleware
        ->
    Route
        ->
    Controller
        ->
    Service
        ->
    Model / External Service / AI
        ->
    HTTP Response

The design deliberately avoids putting domain logic into server.js.

Responsibility split:

    Frontend
        Presentation / map / dashboard / charts / user interaction

    Backend
        API
        validation
        orchestration
        persistence
        snapshots
        integration
        standardized errors
        AI transport bridge
        chat persistence

    AI-Service
        reasoning / agents / LangGraph workflow

    GIS-Service
        coordinate and spatial processing

    Ecosystem-Service
        ecosystem data retrieval / provider-specific normalization

4.1 ANALYSIS SERVICE — MAIN ORCHESTRATOR

File: Backend/src/services/analysis.service.js

Functions: createAnalysis() getAnalysis() getAnalysisStatus()
deleteAnalysis()

createAnalysis performs:

    1. Validate activity/date/time.
    2. Validate zones array.
    3. Generate analysisId.
    4. Format each zone.
    5. Create Analysis Mongo document.
    6. Set status=processing.
    7. Process each zone.
    8. Call GIS.
    9. Call Ocean.
    10. Call Ecosystem.
    11. Call Weather.
    12. Save snapshots.
    13. Set final status:
            completed if no failure
            partial if one or more failures
    14. Update Analysis document.
    15. Return updated analysis.

4.2 GIS STEP

For each zone:

    getGISData({
      latitude,
      longitude
    })

On success: zone.gis = result

On failure: hasFailure=true zone.gis = { status: “error”, data: null,
reason: error.message }

GIS snapshot: variable = “gis_data”

4.6 FINAL STATUS

Current final logic:

    analysis.status =
      hasFailure
        ? "partial"
        : "completed";

This fixed an earlier bug where successful analyses stayed in
“processing”.

Schema still supports: pending processing completed partial failed

The current implementation is synchronous and normally transitions:
processing -> completed or processing -> partial

4.7 PARTIAL FAILURE DESIGN

Example:

    GIS       available
    Ocean     available
    Ecosystem error
    Weather   available

Result: status = partial

Successful data remains stored.

The failed source gets an explicit error/unavailable representation.

This is deliberate and is a core ORCA architecture requirement.

==================================================================== 16.
IMPORTANT DESIGN DECISIONS TO PRESERVE
====================================================================

1.  MULTI-ZONE IS NOT OPTIONAL. Always keep: zones[] zoneId location
    per-zone service data

2.  DO NOT MOVE TO ROOT-LEVEL LAT/LON. A single global coordinate model
    would break the intended multi-zone design.

3.  DO NOT MIX ZONE DATA. Never use array position as the only identity.

4.  DO NOT FABRICATE DATA. Missing environmental data must remain
    null/unavailable/error.

5.  DO NOT FABRICATE RISK OR CONFIDENCE. These must come from the
    appropriate reasoning process.

6.  DO NOT PUT AI REASONING IN NODE. Backend is the
    transport/orchestration boundary.

7.  PRESERVE PROVENANCE. Keep source, timestamp, variable, unit,
    forecast/observation, quality, and status wherever possible.

8.  PRESERVE PARTIAL RESULTS. One upstream failure must not destroy
    successful data.

9.  KEEP PROVIDER-SPECIFIC ECOSYSTEM LOGIC IN ECOSYSTEM-SERVICE. Do not
    spread Copernicus/provider-specific details through the Backend.

10. KEEP ROUTES/CONTROLLERS THIN. Put business logic in services.

11. KEEP server.js AS BOOTSTRAP ONLY.

12. DO NOT COMMIT .env OR SECRETS.

13. STABILIZE API CONTRACTS BEFORE FRONTEND/AI INTEGRATION. Do not
    silently rename fields.
