ORCA AI-SERVICE — DETAILED EXPLANATION
=========================================

1. PROJECT OVERVIEW
-------------------
The project is ORCA, a Marine Intelligence platform designed around an agentic AI architecture.

The AI-Service is the intelligence layer. Its job is to receive structured marine-analysis requests from the Backend, collect/use environmental information through service adapters, run domain-specific agents, combine their results through a LangGraph workflow, and return structured evidence-based decisions.

The intended high-level communication is:

Frontend
   |
   v
Backend
   |
   v
AI-Service
   |
   +--> Weather Service
   +--> Ocean Service
   +--> Ecosystem Service
   +--> Cyclone Service
   +--> Tide Service
   +--> PFZ Service
   +--> GIS Service
   |
   v
Structured Marine Analysis
   |
   +--> Weather Agent
   +--> Ocean Agent
   +--> Ecosystem Agent
   +--> Risk Agent
   +--> Decision Agent
   |
   v
Backend
   |
   v
Frontend


2. IMPORTANT OWNERSHIP RULE
----------------------------

The AI-Service should not directly modify or own:
- Frontend/

4. models/schemas.py
--------------------
This is the structured validation layer.

It defines Pydantic models and enums for:
- AnalysisRequest
- AnalysisResponse
- Zone
- ZoneResult
- WeatherAssessment
- OceanAssessment
- EcosystemAssessment
- RiskAssessment
- DecisionAssessment
- ChatRequest
- ChatResponse
- Evidence
- errors and data-quality states

Important behavior:
- analysisId identifies an analysis.
- zoneId identifies a zone.
- zones must contain unique zoneIds.
- Zone results preserve their zoneId.
- Evidence can contain variable, value, unit, source, timestamp, status, quality, forecast lead time, and notes.
- Data status includes observed, forecast, missing, unavailable, stale, low_quality, and error.
- Risk levels include low, moderate, high, critical, and unknown.

This prevents different agents from returning arbitrary or inconsistent structures.


5. utils/helpers.py
-------------------
This file contains shared utility functions.

It handles:
- UTC timestamps
- datetime normalization
- zone lookup
- unique zone validation
- nested dictionary access
- missing-value checks
- evidence construction
- error construction
- confidence clamping
- confidence reduction for missing components
- safe text handling
- prompt-injection boundary marking

A key design principle is that missing data is preserved instead of silently converted into a value.

The helper for user input also marks user-provided text as untrusted so it cannot override system rules.


6. SERVICES LAYER
-----------------
The services layer is the adapter layer.

Its purpose is to keep provider-specific HTTP/API logic separate from agents.

Weather:
    services/weather_service.py

Ocean:
    services/ocean_service.py

Ecosystem:
    services/ecosystem_service.py

GIS:
    services/gis_service.py

This separation means the agents do not need to know the details of how an external provider is contacted.

If a provider changes, the service adapter can be changed without redesigning the agent.

16. RISK AGENT
-------------
The Risk Agent combines:

    Weather Agent
          +
    Ocean Agent
          +
    Ecosystem Agent
          |
          v
      Risk Agent

It generates:
- risk_level
- risk_factors
- confidence
- failed_domains
- limitations
- summary

Risk levels:
- low
- moderate
- high
- critical
- unknown

The current deterministic implementation uses supplied evidence to identify factors such as elevated wind, gusts, precipitation, low visibility, large waves, long wave period, strong currents, ecological sensitivity, protected areas, sensitive areas, and ecological constraints.

These rules are based only on supplied variables. The agent does not invent environmental measurements.


17. DECISION AGENT
------------------
The Decision Agent converts the risk and domain evidence into an operational recommendation.

It generates:
- zoneId
- risk level
- recommendation
- key reasons
- confidence
- evidence
- limitations
- component summaries
- data quality

Example decision logic:
- Critical: avoid/defer until reassessed.
- High: strong caution; consider postponing or selecting a lower-risk zone.
- Moderate: proceed only with appropriate caution and reassessment.
- Low: no major risk signal identified from supplied evidence.
- Unknown: insufficient evidence for a reliable recommendation.

These are decision-language categories, not invented environmental measurements or legal rules.

The Decision Agent does not independently claim that an activity is legally permitted or prohibited.

22. MULTI-ZONE SUPPORT
---------------------
Multi-zone analysis is a core requirement.

Example:

    Zone A -> zoneId = ZONE_001
    Zone B -> zoneId = ZONE_002
    Zone C -> zoneId = ZONE_003

Every agent receives the zone information and returns the same zoneId.

The system validates that:
- zoneIds are unique
- result zoneId matches the zone
- result maps do not contain unknown zoneIds
- data from different zones is not mixed

This is more reliable than assuming that result[0] belongs to zone 0, result[1] belongs to zone 1, etc.


23. PARTIAL FAILURE HANDLING
----------------------------
The architecture does not require every service to succeed.

For example:

    Weather -> SUCCESS
    Ocean -> SUCCESS
    Ecosystem -> ERROR

The system should preserve the Weather and Ocean results, mark the Ecosystem component as failed, reduce/qualify confidence, and let Risk/Decision communicate the limitation.

It must never replace the missing Ecosystem result with invented data.


24. DATA PROVENANCE
-------------------
Environmental evidence should preserve:

- variable
- value
- unit
- source
- timestamp
- forecast/observation status
- quality
- notes

This allows the final recommendation to be traceable back to the supplied environmental data.

The system is designed so that a value without provenance is not silently treated as high-quality evidence.


25. CONFIDENCE
--------------
Confidence represents evidence quality and completeness.

It is NOT:
- a probability of truth
- a guarantee
- a statistical forecast unless explicitly calculated by a validated model

Confidence can be affected by:
- missing variables
- failed domains
- poor-quality data
- unavailable sources
- stale data
- incomplete evidence

The implementation avoids false precision.

Step 5:

- zones
- zoneId
- coordinates
- planned datetime
- activity/context

Step 6:
LangGraph starts.

Step 7:
Weather Agent obtains/interprets weather evidence.

Step 8:
Ocean Agent obtains/interprets ocean evidence.

Step 9:
Ecosystem Agent obtains/interprets ecological evidence.

Step 10:
Risk Agent combines the domain evidence.

Step 11:
Decision Agent generates the zone-level recommendation.

Step 12:
Finalize validates the zone identity and partial/success state.

Step 13:
AI-Service returns structured results to Backend.

Step 14:
Backend sends the appropriate response to Frontend.

46. IN SIMPLE WORDS
-------------------
You have built the foundation of an agentic marine intelligence backend.

The system takes marine zones and a planned activity/time, gathers environmental evidence, lets separate specialist agents understand Weather, Ocean, and Ecosystem conditions, combines those findings into a Risk assessment, and finally generates a Decision for each zone.

LangGraph controls the sequence.

Pydantic controls the data contract.

Services handle external APIs.

Tools provide controlled access to services.

Agents perform domain-specific intelligence.

Risk combines the domains.

Decision produces the final recommendation.

Chat allows users to ask follow-up questions using the stored analysis context.

The design is multi-zone, evidence-based, provenance-aware, and explicitly handles missing or failed data.
